## 2. 회고분석 배점 [결정됨]

### 2-1. 배경

현재 회고분석은 텍스트 분석 결과(`analysis_content`)만 저장한다. 승률(wins/losses)은 "이겼나 졌나"만 보지만, 회고분석 배점은 **과정의 타당성**을 수치화한다:

- 분석이 맞았는데 운 나빠서 진 것 → 분석 정확도 높음, 수익률 마이너스
- 분석이 틀렸는데 운 좋게 이긴 것 → 분석 정확도 낮음, 수익률 플러스

회고분석 에이전트는 전체 사이클 리포트 + 매매 이력 + RAG 문서를 다 보고 나서 판정하므로 단순 승률보다 정밀하다.

### 2-2. 스키마 변경

`retrospective_analyses` 테이블에 컬럼 추가:

```sql
ALTER TABLE retrospective_analyses ADD COLUMN analysis_accuracy INTEGER;
ALTER TABLE retrospective_analyses ADD COLUMN rag_contribution INTEGER;
```

| 컬럼 | 타입 | 범위 | 설명 |
|------|------|------|------|
| `analysis_accuracy` | INTEGER | 0~100 | 12에이전트 분석의 실제 시장 움직임 대비 정확도 |
| `rag_contribution` | INTEGER | 0~100, NULL | RAG 경험의 PA 판단 기여도. RAG 미사용 시 NULL |

### 2-3. 배점 기준

#### analysis_accuracy (0~100)

12에이전트 파이프라인의 분석이 실제 시장 움직임과 얼마나 일치했는가.

| 점수 | 기준 |
|------|------|
| 90~100 | 방향, 타이밍, 근거 모두 정확. 분석 논리가 시장 결과와 완전히 일치 |
| 70~89 | 방향은 맞았으나 타이밍 또는 근거에 부분 오류. 핵심 판단은 유효 |
| 50~69 | 방향은 맞았으나 근거가 부실하거나 우연히 맞음. 재현 가능성 낮음 |
| 30~49 | 방향이 틀렸으나 일부 분석(섹터, 매크로 등)은 유효 |
| 0~29 | 전반적으로 부정확. 시장 상황을 오독 |

#### rag_contribution (0~100, RAG 미사용 시 null)

RAG로 주입된 과거 경험이 PA 판단에 얼마나 기여했는가.

| 점수 | 기준 |
|------|------|
| 90~100 | RAG 경험이 판단의 핵심 근거. 경험 없이는 다른 결정을 했을 것 |
| 70~89 | RAG 경험이 판단에 유의미하게 반영. 확신도나 비중에 영향 |
| 50~69 | RAG 경험이 언급됐으나 판단에 결정적이지 않음 |
| 30~49 | RAG 경험이 거의 무시됨. 파이프라인 결론에만 의존 |
| 0~29 | RAG 경험이 오히려 판단을 방해하거나 완전히 무관 |

### 2-4. 프롬프트 추가

기존 회고분석 프롬프트 출력 형식에 추가:

```
**Output Format**:
- Reflection: 포괄적 분석 (800-1200 토큰)
- Key Lessons: RAG 쿼리용 간결한 요약 (200-400 토큰)
- analysis_accuracy: 정수 (0~100)
- rag_contribution: 정수 (0~100) 또는 null (RAG 미사용 시)
```

### 2-5. 파싱

```python
import re

def _parse_scores(text: str) -> tuple[int | None, int | None]:
    accuracy = None
    contribution = None

    m = re.search(r'analysis_accuracy\s*[:=]\s*(\d+)', text)
    if m:
        accuracy = max(0, min(100, int(m.group(1))))

    m = re.search(r'rag_contribution\s*[:=]\s*(\d+|null)', text, re.IGNORECASE)
    if m and m.group(1).lower() != 'null':
        contribution = max(0, min(100, int(m.group(1))))

    return accuracy, contribution
```

파싱 실패 시 NULL 저장. 회고분석 결과 자체는 정상 저장.

### 2-6. 대시보드 표시

```
분석 정확도: 72점 (23건 평균)
RAG 기여도: 58점 (RAG 사용 15건 평균)
```

`GET /metrics` 응답에 추가:

```json

  "analysis_accuracy_count": 23,
  "rag_contribution_avg": 58.1,
  "rag_contribution_count": 15
}
```

## 3. 포트폴리오 모드 [결정됨]

### 3-0. 핵심 원칙

포트폴리오 모드는 **기존 분석검증 시스템과 완전히 독립된 별도 시스템**이다.

- 기존 스케줄 시스템(`schedule_configs`, `schedule_jobs` 등)에 mode 컬럼을 추가하지 않는다
- 포트폴리오 전용 테이블을 별도로 만든다
- 자금 풀도 분석검증 자금과 완전히 분리된다 (의도가 다르기 때문)
- 두 시스템이 공유하는 것은 **12에이전트 파이프라인의 분석 결과**(reports 테이블)뿐이다

### 3-1. 결정된 사항

#### 분석검증모드 PA는 변경하지 않는다

분석검증모드는 통제된 실험이다. 변수를 최소화하여 분석 품질을 순수 측정한다.

```
12에이전트 분석 → 고정 결론 → PA(실행자) + 유일한 변수 RAG → 결과
```

PA에 전략 자유도를 주면 "분석이 맞았는지 PA가 잘한 건지" 귀인이 불가능해진다. 분석검증 PA는 실행자로 유지.

#### 포트폴리오 모드는 기존 분석 루프와 완전히 분리된 별도 진입 포인트

기존 `분석 → PA → 요약 → 반성` 루프 안에 포트폴리오 PA를 넣지 않는다.

```
[기존 루프 — 분석검증모드, 변경 없음]
스케줄 트리거 → NVDA 분석+PA+요약 → TSLA 분석+PA+요약 → ... → 전부 완료

[포트폴리오 모드 — 별도 진입]
오늘치 전체 스케줄 완료 감지 → 포트폴리오 큐잉 → 비서 → 포트폴리오 PA → 매매 → (주간) 반성
```

이유: 포트폴리오 PA는 **전체 티커의 분석 결과를 한꺼번에** 봐야 전략을 짤 수 있다. 종목별 순차 루프 안에 넣으면 "NVDA 판단 시 TSLA 분석이 아직 안 끝남" → 전체 비교 불가 → 포트폴리오 전략 수립 불가.

#### 포트폴리오 모드는 활성화/비활성화 개념

환경변수 또는 설정으로 on/off. 활성화 시 오늘치 스케줄이 전부 완료되면 자동으로 포트폴리오 큐잉.

#### 12에이전트 파이프라인은 양 모드에서 동일

분석은 객관적으로 동일하게 수행된다. 모드 차이는 PA 이후에만 발생.

#### 포트폴리오 PA는 별도 클래스 (PortfolioManagerAgent)

프롬프트 분기가 아닌 별도 클래스로 분리. 입력 데이터, 판단 로직, 출력 포맷이 전부 다르기 때문.

| 클래스 | 역할 |
|--------|------|
| `PortfolioAgent` (기존) | 분석검증 PA — 실행자 |
| `PortfolioManagerAgent` (신규) | 포트폴리오 PA — 펀드매니저 |

#### 포트폴리오 PA의 역할

포트폴리오 PA는 **자산운용가/펀드매니저**다. 개별 종목의 타점을 잡는 것이 아니라, **적절한 순간에 적절한 배분(밸런싱)**을 하는 것이 목적이다. 리밸런싱 판단을 스스로 내리고, 그 결과를 매매 지시(JSON)로 출력한다.

#### 포트폴리오 PA 출력 포맷

분석검증 PA와 마찬가지로 **텍스트(판단 근거) + 구조화 JSON(매매 지시)** 형태로 출력한다.

텍스트: 리밸런싱 판단 근거 (시장 상황 인식, 섹터 배분 논리, 리스크 판단)

JSON: 종목별 매매 지시 리스트

```json
[
  {"ticker": "NVDA", "action": "BUY", "allocation_pct": 20, "shares": 5},
  {"ticker": "TSLA", "action": "SELL", "allocation_pct": 0, "shares": 10},
  {"ticker": "AAPL", "action": "HOLD", "allocation_pct": 15}
]
```

아무 종목도 건드리지 않는 전체 HOLD도 유효한 결정이다 (펀드매니저의 "오늘은 유지" 판단).

#### 비서 에이전트

포트폴리오 PA 앞에 비서 에이전트를 배치한다. 모든 티커의 분석 결과를 PA에 직접 넣으면 컨텍스트가 과도하므로, 비서가 압축한다.

**비서 입력**: 각 티커의 **reports 테이블에 저장된 요약 컬럼** (market_report + final_trade_decision) + 현재 포트폴리오 상태 (`portfolio_holdings`). 12에이전트의 원본(raw)이 아니다 — 포트폴리오 모드는 전체 스케줄 완료 후에 실행되므로, 원본은 이미 없고 요약만 DB에 남아있다.

**비서 출력**: 자유 텍스트. 오늘 시장 전체 흐름 + 종목별 핵심 신호 + 포트폴리오 현황 요약.

**LLM 모델**: `deep_think_llm` 사용. 21개 티커의 요약을 압축하면서 핵심 신호를 놓치면 안 되므로.

**비서 출력 = 포트폴리오 RAG 쿼리**: 비서의 자유 텍스트 출력이 그대로 포트폴리오 RAG 검색 쿼리로 사용된다. 예: "테크 섹터 강세, BUY 신호 다수, 현재 테크 편중 35%" → 과거 비슷한 상황에서의 배분 경험 검색.

**비서 출력은 `portfolio_decisions` 테이블에 저장**한다 — 주간 반성 시 "왜 그렇게 배분했는지"의 맥락으로 사용되기 때문.

#### 자동 청산 없음 (포트폴리오 모드)

포트폴리오 PA가 펀드매니저 역할이므로, ±30% 자동 청산 없이 PA 판단에 맡기는 것이 일관적. 분석검증모드의 자동 청산(FR-042)은 그대로 유지.

#### 포트폴리오 PA는 요약하지 않는다

포트폴리오 PA는 요약된 reports를 받아서 읽는 소비자. 자기 산출물을 요약에이전트에 태울 필요 없음.

### 3-2. 공유 자금 풀

포트폴리오 모드는 분석검증 모드의 포지션별 독립 자금(FR-041)과 **완전히 분리된 공유 자금 풀**을 사용한다.

- 총 자금은 **사용자가 입력** (`portfolio_configs` 테이블에 저장)
- 분석검증 모드의 자금(종목당 $5,000 / ₩5,000,000)과는 아무 관련 없음
- 포트폴리오 PA가 이 풀에서 종목 간 배분을 결정

#### 혼합 통화 지원

포트폴리오는 USD 종목과 KRW 종목을 **혼합 보유**한다. 실제 포트폴리오처럼 운용하는 게 목적이므로, 환율 변동도 성과의 일부로 반영한다.

- **기준 통화**: 사용자가 `portfolio_configs`에 설정 (USD 또는 KRW)
- **환율 조회**: `yf.Ticker("USDKRW=X")` — yfinance 실시간 환율
- **환율이 필요한 시점**: 전체 자산 합산, 주간 반성 자산 변동 계산, 대시보드 총 자산 표시
- 반대 통화 종목은 환율로 기준 통화에 환산하여 합산

#### 거래 수수료

실제 포트폴리오 시뮬레이션에 사실성을 부여하기 위해 거래 수수료를 적용한다. 수수료가 있으면 불필요한 리밸런싱을 자연스럽게 억제하는 효과도 있다.

| 시장 | 매수 수수료 | 매도 수수료 | 비고 |
|------|-----------|-----------|------|
| US (나스닥/NYSE) | 0.1% | 0.1% | 일반 브로커 기준 |
| KR (코스피/코스닥) | 0.25% | 0.25% + 증권거래세 0.18% | 일반 증권사 기준. 매도 시 세금 고정 |
| Crypto | 0.1% | 0.1% | 일반 거래소 테이커 기준 |

- `portfolio_configs`에 시장별 수수료율 저장 (사용자 조정 가능)
- 매매 실행 시 `price × shares × fee_rate` 차감
- 매도 시 KR은 증권거래세 0.18% 별도 추가 차감
- `portfolio_trades`에 `fee_amount` 컬럼으로 수수료 금액 기록
- 주간 반성 시 누적 수수료도 성과 평가에 포함

### 3-3. RAG 교차 참조 정책

#### 분석검증 PA → 포트폴리오 반성: ❌ 차단

분석검증 PA가 포트폴리오 반성을 보면 변수 통제가 깨진다. "포트폴리오 편중 때문에 줄여라"는 경험이 분석검증 PA에 주입되면 분석 정확도 측정이 오염.

#### 포트폴리오 PA → 분석검증 반성: ✅ 양방향 참조

포트폴리오 PA는 **분석검증 반성도, 포트폴리오 반성도 모두 참조**한다.

- 분석검증 반성에서 K개 (종목 레벨 교훈: "RSI 70에서 진입하면 손실")
- 포트폴리오 반성에서 K개 (배분 레벨 교훈: "테크 편중 60%에서 급락 경험")

K는 환경변수 `RAG_TOP_K` (기본 1). 각 소스에서 K개씩 가져온다.

| 에이전트 | 읽는 RAG | 안 읽는 RAG |
|----------|----------|-------------|
| 분석검증 PA | 분석검증 반성 K개 | 포트폴리오 반성 ❌ |
| 포트폴리오 PA | 분석검증 반성 K개 + 포트폴리오 반성 K개 | — |

ChromaDB 컬렉션도 모드별 분리: 분석검증 반성 컬렉션 + 포트폴리오 반성 컬렉션.

### 3-4. 포트폴리오 반성

#### 트리거

**주 1회 정기 반성**. 별도 CronTrigger로 **한국시간 일요일 12:00**에 실행.

이 시간이면 비트코인 스케줄(KST 아침 7시)도 이미 돌았고, 한 주의 모든 시장 데이터가 확정된 상태.

포트폴리오 PA의 목적은 타점이 아니라 밸런싱이다. 청산 시에만 반성하면 리밸런싱만 하면서 청산이 안 나는 기간에 데이터가 안 쌓인다. 주간 정기 반성이 밸런싱 품질 평가에 적합.

#### 반성 입력

주간 반성에이전트가 이번 주를 돌아보기 위해 받는 입력 4가지:

1. **이번 주 매매 기록 + 비서 요약** — `portfolio_trades` + `portfolio_decisions.briefing_summary`. 매매 내역만 보면 "왜 이렇게 배분했는지" 맥락을 모르므로, 그때 비서가 준 시장 요약을 같이 줘야 배분의 적절성을 평가할 수 있다.
2. **각 종목의 주간 실제 수익률** — yfinance에서 조회. 주간 가격 변동을 봐야 "NVDA에 40% 넣었는데 10% 올랐다 / TSLA에 30% 넣었는데 5% 빠졌다"를 알 수 있다.
3. **포트폴리오 전체 자산 주간 변동** — `portfolio_holdings` 스냅샷 기반 주초 총자산 vs 일요일 총자산.
4. **현재 포트폴리오 상태** — `portfolio_holdings` 테이블에서 종목별 비중, 현금 잔고.

#### RAG 저장

주간 반성 결과는 **RAG에 태운다** (포트폴리오 전용 ChromaDB 컬렉션 + Postgres 테이블 이중 저장). 포트폴리오 PA가 매일 배분 결정할 때 과거 배분 경험을 RAG로 참조한다.

분석검증 PA는 이 반성을 **참조하지 않는다** (변수 통제).

#### 반성 테이블

포트폴리오 반성은 기존 `reflections` 테이블과 **별도의 `portfolio_reflections` 테이블**을 사용한다.

기존 `reflections`는 `position_id` FK (종목 단위). 포트폴리오 반성은 종목 단위가 아니라 전체 배분 단위이므로 FK 구조가 다르다.

### 3-5. 포트폴리오 전용 테이블 구조

포트폴리오 모드는 기존 7테이블과 별도로 **5개 전용 테이블**을 사용한다.

기존 테이블에 mode 컬럼을 추가하지 않는다 — 포트폴리오 모드는 기존 스케줄 시스템과 완전히 다른 시스템이다.

```
portfolio_configs             ← 포트폴리오 설정 (1 row): 초기자금(사용자 입력), 활성화 여부
portfolio_decisions           ← 포폴PA 1회 결정 단위 (날짜, 비서 요약, PA 판단 텍스트)
portfolio_trades              ← 개별 종목 매매 (decision_id FK, ticker, action, shares, price)
portfolio_holdings            ← 포트폴리오 일별 스냅샷 (ticker, shares, avg_cost, allocation_pct, snapshot_date). 매일 INSERT, 14일 이전 자동 삭제
portfolio_reflections         ← 주간 반성 (reflection, key_lessons, 주간 수익률 등)
```

`portfolio_decisions`가 1회 결정을 묶는 단위가 되고, 하위에 여러 `portfolio_trades`가 붙는 구조.

`portfolio_holdings`는 매일 포폴PA 실행 후 **스냅샷 INSERT**. 14일 이전 데이터는 INSERT 전에 자동 삭제. 주간 반성 시 주초 스냅샷 vs 일요일 스냅샷으로 자산 변동 비교 가능.

두 시스템이 공유하는 것은 **기존 `reports` 테이블의 분석 결과**뿐이다 (비서 에이전트가 읽음).

### 3-6. 전체 흐름

```
[매일 — 분석검증모드, 변경 없음]
CronTrigger → NVDA 분석+PA+요약 → TSLA 분석+PA+요약 → ... → 전부 완료

[매일 — 포트폴리오 모드, 전체 스케줄 완료 후]
오늘치 전체 스케줄 완료 감지
  → 비서 에이전트: reports 테이블 요약 컬럼 읽기 + portfolio_holdings → 자유 텍스트 출력
  → RAG 검색: 비서 출력으로 분석검증 반성 K개 + 포트폴리오 반성 K개 조회
  → 포트폴리오 PA: 비서 요약 + RAG 경험 + 현재 포트폴리오 → 리밸런싱 결정 (텍스트 + JSON)
  → 매매 실행: portfolio_trades 저장 + portfolio_holdings 업데이트
  → portfolio_decisions에 비서 요약 + PA 판단 저장

[주간 — 포트폴리오 반성, KST 일요일 12:00]
CronTrigger (KST Sun 12:00)
  → 이번 주 portfolio_trades + portfolio_decisions.briefing_summary 조회
  → 종목별 주간 수익률 (yfinance) + 전체 자산 변동 + 현재 holdings
  → 반성에이전트: "이번 주 배분이 적절했는가?" 판단
  → portfolio_reflections 저장 + ChromaDB 벡터 저장
```
