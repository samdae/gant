## 1. 자동 청산 메커니즘 부재

**문제**: 현재 포지션 close는 **PA가 전량 SELL을 결정할 때만** 발생한다. 시스템에 손절/익절 자동 트리거가 없어서, PA가 HOLD를 유지하면 -90%든 +500%든 포지션이 **영원히 열린 채로 방치**된다.

**영향**:
- 반성 에이전트가 가동되지 않음 → 학습 사이클이 시작 안 됨
- RAG에 경험 데이터 축적 안 됨 → 시스템의 핵심 가치(자기 개선) 무력화
- 손실이 무한정 확대될 수 있음

**원인 코드**:
- `ticker_scheduler.py:607-611` — PA의 LLM 판단에 100% 의존
- `ticker_scheduler.py:710-722` — `is_closed = trade_action == "SELL" and sell_all` 조건에서만 close 발생. 가격 기반 자동 청산 로직 전혀 없음

**작업**: 사이클 시작 시 현재가 체크 → `return_pct`가 ±30% 초과면 PA를 거치지 않고 즉시 청산. PA가 설정한 `stop_loss`/`target`이 있으면 해당 값 우선 적용, 없으면 ±30% 폴백. 청산 가격은 수집 데이터의 종가 기준 (문제 12 연계)

## 3. 총손익에 실현 손익 미포함

**문제**: 대시보드의 "총손익"이 **미실현 손익(active 포지션)만** 합산한다. 이미 청산한 포지션의 실현 손익은 어디에도 반영되지 않는다.

**영향**:
- GOOGL +2% 수익으로 청산해도 총손익에 0원으로 표시
- 시스템 전체 수익률을 알 수 없음
- 투자 성과 추적이 불가능

**원인 코드**:
- `routes.py:496-519` — `/metrics` API가 `WHERE status = 'active'`로 active 포지션만 순회하여 `total_unrealized_pnl` 계산. closed 포지션의 `return_pct`를 합산하는 로직 없음

**작업**: metrics API에 `total_realized_pnl` 추가, 대시보드에 "실현 손익 + 미실현 손익 = 총손익" 구조로 표시. 통화 혼재 시 금액 합산 불가 → 통화 UI 셀렉터(문제 8 연계)에서 ALL 선택 시 **퍼센트만 표시**, 특정 통화 선택 시 해당 통화 금액으로 표시

## 4. Cash Balance 계산 오류 (이전 포지션 누적)

**문제**: `get_cash_balance()`가 해당 티커의 **전체 trades를 합산**한다. 포지션 close 후 새 포지션이 열리면, 이전 포지션에서의 SELL 수익금이 현재 cash에 합산되어 **자금이 비정상적으로 불어난다**.

**영향**:
- 첫 사이클: $5000 시작 → BUY → 포지션 close (SELL) → cash에 SELL 수익 포함
- 두 번째 사이클: initial_capital $5000 + 이전 SELL 수익 = 실제보다 많은 자금
- 포지션을 반복할수록 매수 가능 금액이 계속 증가하는 부풀려진 자금

**원인 코드**:
- `trade_repo.py:124-144` — `WHERE p.ticker = %s`에 **status 필터가 없어서** closed 포지션의 trades까지 전부 합산

**작업**: **포지션별 독립 자금** 모델 적용. 이 시스템은 자동매매가 아닌 분석 검증 시스템이므로, 각 포지션은 독립적으로 `initial_capital`(기본 $5,000 / ₩5,000,000)을 할당받음. cash_balance = `initial_capital - 해당 포지션의 BUY 합산 + SELL 합산`. 이전 포지션의 trades는 무관. `get_cash_balance()`를 position_id 기반으로 변경

## 5. Win/Loss 0% 판정 불일치

**문제**: 수익률 0%인 포지션이 **반성에서는 win, 대시보드에서는 loss**로 카운트된다.

**영향**: 데이터 일관성 붕괴, RAG 학습 데이터와 대시보드 표시가 불일치

**원인 코드**:
- `reflection.py:112` — `outcome = "win" if return_pct >= 0 else "loss"` (0% = win)
- `routes.py:489-493` — `return_pct > 0`이면 win, `return_pct <= 0`이면 loss (0% = loss)

**작업**: 기준 통일 (둘 다 `>= 0`이면 win, 또는 `> 0`이면 win으로 일원화)

## 8. 통화(Currency) 미지원 — 매매 로직부터 UI까지

**문제**: 시스템 전체에 통화 개념이 없다. `initial_capital`이 USD $5,000 고정인데, KRW 티커(005930.KS 등)의 가격은 원화(₩80,000)로 반환된다. PA가 매수 수량을 `cash / current_price`로 계산하므로, **KRW 종목은 $5,000 ÷ ₩80,000 = 0.0625주**가 되어 사실상 매매가 불가능하다.

**영향**:
- KRW 티커 매수량이 극소수점 → 무의미한 포지션
- 총손익 계산에서 KRW 금액과 USD 금액이 단위 무시하고 합산
- 수익률은 비율이라 통화 무관하게 정상이지만, 금액 기반 지표(PnL, 총투자금)는 전부 오류
- UI에서 모든 금액이 `$` 접두사로 표시 (KRW도 $80,000으로 표시)

**원인 코드**:
- `portfolio_agent.py:525-530` — `shares = cash / current_price` 에서 cash는 USD 기준, price는 yfinance 원화 반환. 단위 불일치
- `trade_repo.py:114-144` — `get_cash_balance()`에 통화 개념 없음. KRW trades의 금액이 USD initial_capital에 합산
- `positions` 테이블 — `avg_cost`에 통화 구분 없음
- `trades` 테이블 — `price`에 통화 구분 없음
- `schedule_configs` 테이블 — `currency` 컬럼 없음. 티커 등록 시 통화 지정 불가
- `format.ts:1-18` — 통화 파라미터는 준비되어 있으나 항상 `$` 기본값 사용

**작업**:
- `schedule_configs`에 `currency TEXT DEFAULT 'USD'` 컬럼 추가 (티커 등록 시 자동 감지: `.KS`/`.KQ` → KRW, `BTC-USD` 등 → USD, 기본 → USD)
- `schedule_configs`에 `initial_capital DOUBLE PRECISION DEFAULT 5000` 컬럼 추가 (KRW 티커는 5000000, USD 티커는 5000. 고정값이지만 향후 사용자 설정 확장 대비 DB 저장)
- `positions`, `trades`에 `currency TEXT` 컬럼 추가
- PA의 cash 계산을 해당 포지션의 통화/initial_capital 기준으로 수행
- 총손익/metrics 계산 시 통화별 분리 (환율 변환 안 함)
- **UI 공통 헤더에 통화 셀렉터 추가**: `G-ANT    ALL [KRW|USD]`
  - **ALL**: 전체 티커 표시, 손익은 **퍼센트만** 표시 (금액 합산 불가)
  - **KRW**: KRW 티커만 표시, 손익을 ₩ 금액으로 표시
  - **USD**: USD 티커만 표시, 손익을 $ 금액으로 표시
  - 기본값 ALL, 선택 시 localStorage에 저장

## 9. 스케줄 테이블 구조 재설계 — schedules 제거 + schedule_configs 확장

**문제**: 스케줄 관련 테이블이 3개(`schedule_configs`, `schedules`, `schedule_jobs`)인데, `schedules`와 `schedule_jobs`가 사실상 **1:1 관계**로 중복이다. 또한 `interval_days`가 `schedule_configs`와 `schedules` 양쪽에 존재하며, 사이클 번호를 매번 `SELECT MAX(scheduled_cycle)`로 조회하는 비효율이 있다.

**현재 구조**:
```
schedule_configs (설정) ─────────────────── 1:N 관계 없음(직접 FK 없음)
schedules (사이클 기록) ─── 1:1 ── schedule_jobs (실행 상태)
                         ─── 1:N ── reports
                         ─── 1:N ── schedule_job_events
```

**영향**:
- `schedules`와 `schedule_jobs`가 1:1인데 별도 테이블 → 불필요한 JOIN
- `interval_days` 중복 (schedule_configs에도, schedules에도)
- 사이클 번호 조회에 매번 `MAX()` 집계 쿼리 (2곳 중복)
- schedule_id FK가 11개 파일 155회 참조 → 코드 복잡도 증가

**원인 코드**:
- `database.py:94-100` — `schedules` 테이블 정의 (ticker, interval_days, scheduled_cycle, created_at)
- `database.py:178-186` — `schedule_jobs` 테이블 정의 (schedule_id FK, status, error_*)
- `schedule_repo.py:77-98` — `get_latest_cycle()`: `SELECT MAX(scheduled_cycle)` 집계
- `ticker_scheduler.py:199,456` — 2곳에서 `get_latest_cycle()` + 1 중복 패턴

**작업** (DB 리셋 시 일괄 적용):
1. `schedules` 테이블 제거
2. `schedule_configs`에 `current_cycle INTEGER DEFAULT 0` 추가 — 원자적 증가로 사이클 관리
3. `schedule_jobs`에 `schedule_config_id BIGINT FK REFERENCES schedule_configs(id)`, `scheduled_cycle INTEGER` 추가 — 사이클별 실행 기록 역할 흡수. ticker는 직접 넣지 않고 FK로 참조 (정규화)
4. FK 변경: `reports.schedule_id` → `reports.schedule_job_id`, `schedule_job_events.schedule_id` 제거 (이미 `schedule_job_id` 있음)
5. `schedule_repo.py` 제거, 관련 로직을 `schedule_config_repo.py` + `schedule_job_repo.py`로 이관
6. `routes.py`, `ticker_scheduler.py` 등에서 `schedule_id` 참조를 `schedule_job_id`로 변경

**목표 구조**:
```
schedule_configs (설정 + current_cycle + currency + initial_capital + market)
schedule_jobs (schedule_config_id FK + cycle + 상태) ─── 1:N ── reports
                                                      ─── 1:N ── schedule_job_events
```

## 10. DB 리셋/마이그레이션 메커니즘 부재

**문제**: `init_schema()`는 `CREATE TABLE IF NOT EXISTS`와 `_ensure_column()`만 제공한다. 테이블을 **드랍하고 재생성하는 리셋 스크립트가 없다**. 스키마 변경(currency 컬럼 추가, current_cycle 추가 등)을 적용하려면 FK 의존성 순서(reflections → trades → reports → schedule_jobs → schedule_job_events → positions → schedules → schedule_configs)를 고려하여 수동으로 DROP 해야 한다.

**영향**:
- 스키마 변경 시 수동 DROP 필요 → 실수로 순서 틀리면 FK 제약 위반 에러
- 테스트 데이터 정리 시 TRUNCATE도 FK 순서 맞춰야 함
- 개발/운영 환경 전환 시 클린 리셋 불가

**원인 코드**:
- `database.py:70-234` — `init_schema()`에 CREATE/ALTER만 존재, DROP 로직 없음
- `scripts/init_db.py` — 초기화만 수행, 리셋 옵션 없음

**작업**:
- `scripts/reset_db.py` (또는 `init_db.py --reset` 플래그) 추가
- FK 의존성 역순으로 `DROP TABLE IF EXISTS ... CASCADE` 실행 후 `init_schema()` 재호출
- **ChromaDB 컬렉션도 함께 삭제** (PostgreSQL reflections와 ChromaDB 벡터의 정합성 유지)
- 운영 환경 오실행 방지를 위해 `--confirm` 플래그 또는 환경 변수 체크 포함
- schedule_configs 보존 여부: DB 전체를 날리는 것이므로 별도 보존 불필요. 티커 설정은 config 파일에서 재등록

## 11. 스케줄러 시장별 실행 시간 미분리

**문제**: 현재 스케줄러는 `IntervalTrigger(days=N)`으로 단순 N일 간격 실행이다. **시장 장마감 시간 개념이 없어서** 모든 티커가 동일한 타이밍에 분석된다. 나스닥/코인과 코스피/코스닥은 장마감 시간이 다르므로, 최신 종가 데이터가 확정된 이후에 분석해야 정확하다.

**영향**:
- 한국장이 아직 열려 있는 시간에 코스피 티커 분석 → 당일 종가 미확정 상태의 데이터 사용
- 장 중 가격 변동이 반영되지 않은 불완전한 분석 결과

**원인 코드**:
- `ticker_scheduler.py:264` — `IntervalTrigger(days=interval_days)`: 시간대 구분 없는 단순 간격
- `ticker_scheduler.py:235-277` — `add_ticker()`에 시장 구분 파라미터 없음
- `schedule_configs` 테이블 — 시장/타임존 컬럼 없음

**작업**:
- `schedule_configs`에 `market TEXT` 컬럼 추가 (값: `us`, `kr`, `crypto` 등). 티커 등록 시 자동 감지 (`.KS`/`.KQ` → kr, 기본 → us)
- `IntervalTrigger` → `CronTrigger`로 변경:
  - **나스닥+코인**: 미국 장마감 1시간 후 (ET 17:00 = KST 07:00)
  - **코스피/코스닥**: 한국 장마감 1시간 후 (KST 16:30)
- `interval_days`는 DB에 유지하되 **당분간 1(매일)로 고정**. 향후 격일 등 확장 시 사이클 시작 시 `current_cycle % interval_days != 0`이면 스킵하는 방식
- **주말/공휴일 처리**: 이미 `last_data_date` 체크로 해결됨 — yfinance에 새 데이터 없으면 `"Skipped (no new data)"` 처리 (`ticker_scheduler.py:508-525`). 추가 작업 불필요

## 12. 매매 시점/가격이 현재 시각 기준

**문제**: 매매(trade) 기록의 `executed_at`이 `datetime.now()`로 설정된다. 분석 파이프라인이 장 마감 후 수 시간 뒤에 실행되므로, 실제 매매 시점은 **수집된 주가 데이터의 마지막 날짜(종가 확정일)**가 되어야 한다. 가격도 해당 날의 종가여야 한다.

**영향**:
- 매매 기록 시간이 새벽 3시 등 비현실적 시각으로 기록
- 문제 11(시장별 스케줄링)이 해결되더라도, 파이프라인 실행 시간 ≠ 데이터 기준일이므로 별도 수정 필요
- 포지션의 `opened_at`도 실제 데이터 기준일이 아닌 코드 실행 시각

**원인 코드**:
- `trade_repo.py:46` — `executed_at = datetime.now().isoformat()`: 현재 시각 하드코딩
- `ticker_scheduler.py:588` — `today = datetime.now().strftime("%Y-%m-%d")`: 파이프라인에 전달하는 날짜도 현재 시각 기준
- `ticker_scheduler.py:997-1008` — `_get_current_price()`에서 yfinance 히스토리의 마지막 날짜를 이미 감지하고 있으나, 이 날짜 정보를 반환하지 않음 (가격만 반환)

**작업**:
- `_get_current_price()` → `_get_latest_close()` 리팩토링: `(price, date)` 튜플 반환
- `trade_repo.create()`에 `executed_at` 파라미터 추가 (외부에서 주입 가능하게)
- `ticker_scheduler.py`에서 yfinance 데이터의 마지막 날짜를 `trade_date`, `executed_at`, `opened_at`에 사용
- `positions.opened_at`도 동일하게 데이터 기준일로 설정

## 13. 회고/반성(Reflections) 웹 UI 미구현

**문제**: 백엔드 API `/reflections`는 구현되어 있으나(FR-025), **프론트엔드에 reflections 관련 코드가 전혀 없다**. 포지션 종료 후 생성되는 회고/반성 내용을 웹에서 확인할 방법이 없다.

**영향**:
- 시스템의 핵심 학습 루프(분석→매매→회고→개선)에서 회고 결과를 사용자가 볼 수 없음
- AI가 무엇을 배웠는지, 어떤 교훈을 얻었는지 불투명
- 승패 분석과 회고 내용 연계 불가

**원인 코드**:
- `routes.py:980-1020` — `/reflections` API 구현됨 (outcome 필터, cursor 페이지네이션 지원)
- `apps/web/src/` — reflections 관련 컴포넌트/라우트 0건. `endpoints.ts`에도 reflections 호출 없음

**작업**:
- `endpoints.ts`에 `fetchReflections()` API 호출 함수 추가
- `/reflections` 라우트 + `Reflections.svelte` — 전체 회고 목록 페이지
  - win/loss 필터 (백엔드 `outcome` 파라미터 활용)
  - cursor 기반 페이지네이션 (백엔드 이미 지원)
  - 표시 항목: reflection 본문 (마크다운), key_lessons, outcome(win/loss), return_pct, market/sector/industry, created_at
- 네비게이션에 "회고" 메뉴 추가

## 14. OpenAI Codex(GPT-5.3) LLM Provider 추가

**문제**: 현재 LLM 프로바이더가 Google 계열(antigravity, gemini-cli)만 지원된다. OpenAI Codex(GPT-5.3)를 OAuth 기반으로 추가하여 프로바이더 선택지를 넓히고자 한다.

**현재 구조**:
- `llm_clients/factory.py` — `"gemini-cli"` 또는 `"antigravity"` 2가지만 지원
- `default_config.py` — `deep_think_llm`과 `quick_think_llm` 2종 모델 분리
- `ChatAntigravity(BaseChatModel)` — LangChain 커스텀 모델로 Google OAuth + 내부 API 호출

**작업**:
- `oauth-codex` PyPI 패키지 의존성 추가 (`pyproject.toml`)
- `llm_clients/codex_client.py` 신규 — `ChatCodex(BaseChatModel)` LangChain 래퍼 생성
  - `oauth-codex`의 `CodexOAuthLLM`을 내부적으로 사용 (OAuth PKCE, 토큰 캐시 자동 처리)
  - 엔드포인트: `chatgpt.com/backend-api/codex/responses`
  - 토큰 캐시: `~/.oauth_codex/auth.json` 또는 keyring
- `factory.py`에 `"codex"` 프로바이더 추가
- **모델은 `gpt-5.3-codex` 단일** — `deep_think_llm`과 `quick_think_llm` 모두 동일 모델 사용
- `default_config.py`에서 `LLM_PROVIDER=codex` 시 모델명 자동 설정
- 첫 실행 시 브라우저 OAuth 필요, 이후 자동 갱신
